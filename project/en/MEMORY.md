**Structuring decisions of the view** — a Sankey visually asserts conservation, which the diagram does not; two consequences handled explicitly rather than hidden: (1) the **hub imbalance** (conversion losses, noise) is a named grey ribbon, symmetric in both directions ("Pertes & conversion" / "Écart de mesure"), so the two columns have the same height by construction; (2) the **unmeasured direct draw** (without Smart CT) keeps a hatched band of **fixed off-scale thickness** + a hatched cap on the House node's bar — a proportional width would invent a value, omitting it would assert zero. Geometry: columns aligned at the TOP with the direct draw in the top slot of both columns → it flows above the hub and **crosses no ribbon**, with no ordering heuristic. **No floor thickness per flow** (a minimum would put the sum of ribbons out of step with the bars' height): flows ≤ 1 W are discarded, same threshold as `EnergyFlowView`. Values strictly identical in both views (`EnergyMath`, signed `batteryFlow`, `flowText` ▲/▼).

**Method lesson (costly, to remember)**: code reading and pencil verification had let through **three real visual defects** (dashes drawn over the whole ribbon thickness → slabs perpendicular to the path, barcode on thick bands; labels that overlapped at the bottom of the column and were truncated on the right; hub label placed on the lowest ribbon). They only showed up by **rendering the view as PNG and looking at it**. For any graphical view: render and look, never conclude from reading the code.

**Capture harness** (disposable, outside the repo, reproducible): app sources compiled separately with `swiftc` (`Updater` stubbed — Sparkle not linkable outside Xcode), packaged as `.app` under a **distinct** bundle id with a **copy** of the preferences (never writes to the real app's domain). **Trap of identifiers of an object migrated on the fly**: a computed property that rebuilds a `PanelArray` from the old `sunPeakWatts` key generates a new `UUID` at each read — any identity binding fails silently (the first setting was lost). The migration must be materialized in storage on opening. Applies to any future soft migration.

**A SwiftUI view that compiles is not a view that works**: the panel array editor compiled and passed review, but rendered for real it was shattered — in a grouped `Form`, each child of a `VStack` becomes a separate row and the first one becomes the label column. It must be composed explicitly (full-width row as `HStack`, sliders as `LabeledContent`). Method corollary: any new settings view must be *rendered* in the harness before being declared finished, not only compiled. This is also why `SunSettingsTab` is internal and not `private`.

**Azimuth convention, never to be mixed**: everywhere in the project, 0° = north, 90° = east, 180° = south, 270° = west (`SunCalc.Ephemeris.azimuth` and `PanelArray.azimuth` are in the same frame). Many solar tools use south = 0: a silent conversion would skew the incidence without breaking anything.

**Yield model** (`SolarGeometry`): 85% direct × cos(incidence) × Meinel atmospheric transmittance (0.7^(air mass^0.678), normalized to 1 at zenith) + 15% diffuse × sin(elevation) × (1+cos tilt)/2, all × 0.9 for losses. The transmittance is indispensable: without it a west facade announced 323 W at sunset instead of 30 W. `cosIncidence` alone remains pure geometry and is exactly sin(elevation) when flat — that is the test locking the convention.

**1.10 captures — two harness refinements** (2026-08-09): (1) give the rendered view's root an **opaque background** (`.background(Color(nsColor: .windowBackgroundColor))`) — without it, texts in semantic colors OUTSIDE cards (panel header, connection footer) go through the backdrop's vibrancy layer that `cacheDisplay` does not capture: they vanish from the capture and the background comes out black; (2) **no need for a .app bundle** if all notifications are disabled in the harness defaults before `Monitor()` (UserNotifications is then never touched) — a bare CLI binary is enough, with `WindowPolicy`/`Updater` stubs and injection of synthetic data into Monitor's `@Published` (poll neutralized: empty host + pollInterval 60 s, inject after the first failure).

**Visual verification outside the app** (method to reuse): compile the sources into a harness binary with `swiftc -target arm64-apple-macos14.0` excluding `ZendureMonitorApp.swift`, `Updater.swift` (Sparkle) and `MenuView.swift`, and providing a `WindowPolicy` stub. Two traps: `Monitor()` needs `NSApplication.shared` (it touches `NSApp.appearance`) and a real `.app` bundle (UserNotifications refuses `bundleProxyForCurrentProcess is nil`); and `ImageRenderer` does not run the SwiftUI lifecycle (no `onAppear` → empty weather card, `NSApp.appearance` ignored). For a full capture: host the view in an `NSHostingView` + `NSWindow`, let the `RunLoop` run a few seconds, then `cacheDisplay(in:to:)`. The theme is forced with `.environment(\.colorScheme, .dark)`, the language with `-AppleLanguages '(en)'` + copy of `en.lproj` into the harness bundle.

**String extraction**: `xcodebuild ... SWIFT_EMIT_LOC_STRINGS=YES` writes a `<File>.stringsdata` (JSON, key `tables.Localizable`, list of `{key, location}` entries) in `Build/Intermediates.noindex/.../Objects-normal/arm64/`. It is the authoritative list of expected keys (with the right `%lld`/`%@` specifiers): comparing it to the catalog avoids inventing keys that will never be used.

## Key technical facts
- **Info.plist is generated by xcodegen** from `project.yml` (`info.properties`): never edit Info.plist directly, any key (e.g. NSLocation*UsageDescription) must be added in project.yml otherwise it is overwritten at the next `xcodegen generate`. Same for ZendureWidget/Info.plist.
- **Local-network TCC — replacing the app breaks the grant** (observed 2026-08-05, clarified 2026-08-06): reinstalling a new build in /Applications loses the "local network" authorization AND may break the Finder icon — root cause: **stale LaunchServices registration**. Fix that works: `lsregister -f /Applications/App.app` + app restart (the Settings toggle and `killall nehelper` are not enough alone). Residual white icon: `touch` + `killall iconservicesagent Finder`. Signature diagnosis: gateway ping OK (exempt) but LAN clients in "No route to host" while ARP sees them. ⚠️ Via Tailscale/utun the blocking is invisible (the authorization does not apply to the VPN) — always diagnose from the LAN.
- **Local-network TCC**: the grant belongs to the app in /Applications (Developer ID). Dev builds launched from build/ are silently denied (poll fails, curl OK). To test live: sign with Developer ID and install in /Applications. To test the UI without a device: python mock on 127.0.0.1 (not subject to TCC) + ImageRenderer harness (scratchpad).
- UI: components MetricCard/SparklineChart/CircularGauge/LegendRow taken from MacInside (~/Documents/GitHub/MacTools/MacInside) — keep both apps visually aligned.
- Local API (zenSDK, official): HTTP port 80 on the device, `GET /properties/report` → JSON. mDNS `_zendure._tcp`, hostname `Zendure-<model>-<mac>`.
- Fields: `solarInputPower` (W), `electricLevel`/`socLevel` (%), `outputHomePower`, `gridInputPower`, `packInputPower` (discharge), `outputPackPower` (charge), `solarPower1…6`.
- Control would use `POST /properties/write` with `{"sn": …, "properties": {…}}` — not used yet (read-only app).
- Refs: github.com/Zendure/zenSDK (docs/de.md, docs/en_properties.md), github.com/Gielz1986/Zendure-HA-zenSDK.
